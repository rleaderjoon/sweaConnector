갱신이 많고 조회가 적다면, **갱신할 때는 기록만 하고 조회할 때 몰아서 계산**한다.
문제를 읽고 코드를 쓰기 전에 호출 횟수를 세는 이유가 이것이다.

## 판정식

```
조회 횟수 x 조회 1회 비용  <  제한 시간
```

갱신 비용은 이 식에 거의 등장하지 않는다. 갱신이 20,000번이고 조회가 100번이라면,
조회 한 번에 전체를 다시 계산해도 O(20,000 x 100) = 2백만 — 아무 문제 없다.
반대로 갱신마다 상태를 정확히 유지하려 들면 갱신 20,000번 각각이 비싸진다.

## 무엇을 "기록"으로 둘 것인가

기록은 **추가만 하는 자료구조**여야 의미가 있다.

| 갱신 | 기록 방식 |
|---|---|
| 추가 | 배열 끝에 append |
| 삭제 | 삭제 플래그만 켜기 (실제로 안 지운다) |
| 수정 | 최신 값으로 덮어쓰기 |

조회 때는 플래그가 꺼진 것만 훑으면서 계산한다. 삭제된 원소를 배열에서 실제로 당겨오는
O(N) 이동이 사라지는 것이 큰 이득이다.

## 이 패턴이 깨지는 경우

조회가 갱신만큼 많아지면 매번 전체 계산이 그대로 O(갱신 x 조회) 로 터진다. 그때 두 가지 탈출구가 있다.

**dirty 플래그 + 캐시** — 조회가 연속으로 들어오는데 그 사이 갱신이 없으면 이전 결과를 그대로 준다.

```java
boolean dirty = true;
int cached;

void update(...) { /* 기록 */ dirty = true; }

int query() {
    if (dirty) { cached = recomputeAll(); dirty = false; }
    return cached;
}
```

**부분 갱신** — 갱신이 건드린 범위만 다시 계산한다. 여기서부터 세그먼트 트리나 BIT 같은
자료구조가 필요해진다. 다만 그 단계로 넘어가기 전에 위 두 가지를 먼저 시도하는 편이
구현 시간이 훨씬 짧다.

## 습관으로 만들 것

문제를 읽으면 코드보다 먼저 호출 횟수 표를 적는다.

| 함수 | 최대 호출 | 1회 예산 |
|---|---|---|
| | | |

이 표를 채우지 않고 시작한 설계는 대부분 자료구조 선택에서 실패한다.
알고리즘을 몰라서 시간 초과가 나는 경우보다, 호출 분포를 안 보고 시작해서 나는 경우가 많다.
